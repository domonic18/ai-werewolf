# AI 狼人杀 · Agent 补位局 宪法

> 本文件是项目的最高约束。所有 `specs/`、`plan.md`、`tasks.md` 与实现必须符合本宪法；
> 与之冲突的方案一律驳回或先修订宪法。技术细节见 `docs/TECH-STACK.md`，Agent 行为规范见 `AGENTS.md`。

## Core Principles

### I. LLM 单一事实源（NON-NEGOTIABLE）

AI 玩家的每一句发言、每一次行动（狼刀目标、查验对象、女巫用药、投票对象、首夜遗言）都必须来自大模型实时生成，**禁止**任何规则化话术、模板兜底、随机挑选、"看起来像人话"的降级文案。

- LLM 调用失败或输出不合法时，**MUST** 以明确原因中止对局（fail-fast），并向玩家说明「模型不可用 / 输出不合法」，而非用假数据继续。
- 提示词可以注入人设、私有信息与历史记忆（这些是"角色的处境"，不是"角色的台词"）。
- 判定标准：任何 AI 输出必须能追溯到一次具体的模型调用记录；测试中禁止 mock 出语义内容来"验证体验"。

**理由**：产品的唯一卖点是"和真正的智能体玩"。一旦允许兜底，退化成脚本游戏，产品价值归零。

### II. 服务端权威与信息隔离（NON-NEGOTIABLE）

所有身份分配、随机数、夜晚行动、结算与胜负判定只存在于服务端（`src/game/engine.js`）；客户端是薄渲染层。

- 前端 **MUST NOT** 包含任何游戏规则判断或身份推断逻辑，也不得从接口反推出未公开信息。
- 夜晚阶段的事件流、日志、错误信息 **MUST NOT** 出现「玩家名 + 行为词」的共现；身份泄露视为 P0 缺陷。
- 观战者与已出局玩家看到的是脱敏快照；真人玩家的私有信息（身份、队友、验人结果）只随本人的 `snapshot(forPlayerId)` 下发。
- 任何"为了调试方便"而在响应中附带全量状态的做法一律禁止。

**理由**：狼人杀的全部乐趣建立在信息不对称上。一次泄露即摧毁整局体验，且不可事后修复。

### III. 规范先行，无合同不编码

每条进入开发的需求 **MUST** 在 `specs/<编号>-<特性>/` 下有 `spec.md`（用户故事 + EARS 验收条款），并配套 `plan.md` 与 `tasks.md`。

- 需求描述使用 EARS 句式：`当 <触发>` / `如果 <条件>` / `在 <状态> 时`，系统 SHALL/MUST `<可观测行为>`。
- 每条 FR 必须可被一条验收场景或一条自动化测试验证；无法验证的条目要么删除，要么明确标注为「人工验收」。
- 实现与合同不一致时，先改合同（同一次提交内），不允许"代码先行、文档后补"。
- `docs/PRD.md` 是产品全景，`specs/` 是它的可执行切片；冲突以 specs 为准并回写 PRD。

**理由**：这是一个会被反复迭代的 AI 应用，规则复杂度（10 个角色 × 6~12 人局 × 夜晚/白天多阶段）靠记忆维护必然出 bug。

### IV. 三层可验证性（NON-NEGOTIABLE）

每个变更 **MUST** 通过 `npm test` 的完整三层：

1. **单元层**：`tests/json.test.js` 类——纯函数与解析器（JSON 提取、玩家名匹配、角色判定）。
2. **引擎层**：`tests/engine-smoke.test.js` 类——Mock LLM 驱动的整局冒烟（≥10 局），断言不变量而非文案。
3. **链路层**：`tests/api-selftest.test.js` 类——进程内起服务，走完 创建 → 行动 → 结算 的真实 HTTP 路径。

- 断言 **MUST** 针对结构、状态与不变量（如「夜晚事件流不含玩家名」「投票数等于存活人数」），**MUST NOT** 断言 LLM 生成的具体文字。
- 修改规则、角色、夜晚流程时，额外跑隐私审计（夜晚事件流扫描），结果留档在提交信息或 `specs/<feature>/` 下。
- 只跑本地 curl 不算验证：沙箱会劫持 127.0.0.1，必须用进程内自测。

**理由**：LLM 输出不可复现，只有把断言放在不变量上，测试才稳定；而规则 bug 恰恰出现在不变量被破坏时。

### V. 版本可追溯、可回滚

- 每次对外可见的迭代 **MUST** 同步递增版本号（`package.json` 与页面底部 `#ver`），便于线上核对是否为新版。
- 静态资源 **MUST** 禁缓存或带指纹（`Cache-Control: no-cache` + 构建 hash），避免"用户看到旧界面"。
- 每个迭代 **MUST** 可独立回滚：不破坏既有 HTTP 契约（`/api/games`、`/events`、`/action` 等字段只增不删）。
- 破坏性变更新增版本号字段或新端点，禁止原地改语义。

**理由**：产品长期运营在个人站点，线上问题只能靠版本号定位与快速回滚止血。

### VI. 开源卫生与最小依赖

- 仓库 **MUST NOT** 包含任何密钥、token、云服务凭据；配置以 `config/*.example.json` 模板 + 环境变量注入。
- 新增依赖前 **MUST** 说明理由与体积代价；能用标准库解决的不得引框架。
- 对外文档（`README.md`、`AGENTS.md`、`specs/`）**MUST** 保持与实际实现一致，不允许存在"文档写了但代码没有"的功能描述。

**理由**：项目是参赛作品兼公开仓库，凭据泄露与文档失真都会直接损害可信度。

## 技术约束（Technology Constraints）

| 层 | 约束 |
|---|---|
| 运行时 | Node.js ≥ 18，原生 `http`，零 Web 框架；部署为单端口服务并绑定 `0.0.0.0:$PORT` |
| 前端 | 移动优先（390px 基准）；不引入 SSR/文件路由框架；构建产物由现有 Node 服务托管 |
| AI | 仅通过 WorkBuddy Cloud LLM（服务端调用，免密钥）；模型可切换，默认 flash 级控制成本 |
| 存储 | 仅使用 WorkBuddy Cloud Database；不引入外部数据库/缓存/消息队列 |
| 部署 | WorkBuddy sites；沙箱不注入自定义环境变量，配置须有文件兜底路径 |

技术栈升级以 `docs/TECH-STACK.md` 的 ADR 为准；ADR 未通过前，实现必须停留在现有栈。

## 开发流程（Development Workflow）

1. **选需求**：从 `docs/PRD.md` 取一条 R 编号，建 `specs/<编号>-<特性>/spec.md`。
2. **澄清**：开放问题（Q1~Q5 式）在 spec 中显式列出，未闭环不得进入 plan。
3. **方案**：`plan.md` 写技术路径、契约变更、影响面与回滚方式；通过宪法检查表。
4. **拆任务**：`tasks.md` 拆到 ≤ 2 人日粒度，每条标注验收方式。
5. **实现**：按任务顺序提交，保持单一目的；不夹带无关重构。
6. **验收**：三层测试 + 隐私审计（如涉及）+ 390px 手动走查；线上发版核对版本号。
7. **回写**：PRD 状态、版本路线图、`AGENTS.md`（如规则变更）同步更新。

**质量闸门**：`npm test` 未全绿不得发版；宪法第 I / II 条任何一项被违反不得合并。

## Governance

- 宪法优先于一切实践、模板与个人习惯；`AGENTS.md` 与本文件冲突时以本文件为准。
- 修订宪法 **MUST** 说明：改动哪条、为什么、影响哪些已有 specs，并递增版本号。
- 每次 spec 评审 **MUST** 检查宪法检查表（`plan.md` 中「Constitution Check」段落）。
- 复杂度必须被证明必要：引入新依赖、新抽象层、新存储，都在 plan 中写明"不做会怎样"。
- 运行时开发指引见 `AGENTS.md`；产品全景见 `docs/PRD.md`。
