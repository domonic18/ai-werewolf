# Feature Specification: 游戏大厅与对局观战

**Feature Branch**: `001-lobby-spectate`

**Created**: 2026-10-22

**Status**: Draft（含 1 项待确认开放问题 Q3）

**Input**: 用户描述："游戏大厅与对局观战：大厅列表、观战模式、投票可视化"（对应 `docs/PRD.md` R3.2、R6.3）

**范围边界**：本特性只交付「发现对局 → 进入观战 → 看懂局势」的只读链路，以及大厅的可扩展列表。
账号登录（R3.1）、建局角色配置（R4）、真人房（R7）不在本特性内。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 在大厅发现并进入一局（Priority: P1）

玩家打开网站，首页能看到「正在进行的对局」与「我的对局」两个入口；点进大厅能看到全量对局列表（房主、人数、阶段、存活比、观战人数）；点任意一局即可进入观战，或从大厅直接开一局新的。

**Why this priority**：这是当前产品最大的结构性缺口——首页只能开局，别处来的流量看不到"这里有活人对局"，无法形成停留与二次访问。没有大厅，产品永远只是一次性 demo。

**Independent Test**：在已有 ≥3 局进行中的环境下打开大厅，能列出全部对局且字段正确；点任意一局进入观战，看到与对局同步推进的事件流。

**Acceptance Scenarios**：

1. **Given** 服务端存在 3 局进行中的对局，**When** 玩家打开大厅，**Then** 列表按观战人数降序展示 3 条记录，每条含房主名、当前人数/上限、阶段标签（第 N 天·投票 / 第 N 夜）、存活比。
2. **Given** 玩家在大厅，**When** 点击某局的「观战」，**Then** 3 秒内进入观战视图，并开始接收该局的实时事件。
3. **Given** 服务端没有任何进行中的对局，**When** 玩家打开大厅，**Then** 展示空态（文案 + 「开一局」按钮），不展示空白列表或报错。

---

### User Story 2 - 观战者看到"上帝视角"但不破坏对局公平（Priority: P1）

观战者能看到所有玩家的身份、阵营存活进度、每晚发生了什么；但观战内容不得以任何形式回流给正在对局的玩家（避免场外报信息）。

**Why this priority**：观战是拉新与留存的核心场景，但狼人杀的观战天然与公平性冲突。做错一次（观战页泄露给玩家）就是产品级事故。

**Independent Test**：以观战身份与对局玩家身份分别请求同一局，对比两份快照：观战快照含全量身份；玩家快照只含自己的身份与已公开信息；且玩家快照中不出现任何其他玩家身份字段。

**Acceptance Scenarios**：

1. **Given** 一局进行到第 2 夜，**When** 观战者拉取快照，**Then** 拿到全部玩家身份与当前夜晚进度，且不含「谁正在行动」的明文。
2. **Given** 同一局，**When** 对局中的真人玩家拉取快照，**Then** 只能看到自己的身份、队友（若为狼）与自己收到的信息，其他玩家身份字段缺失。
3. **Given** 观战者已出局或从未参与该局，**When** 观战者尝试提交任何 `action`，**Then** 服务端拒绝（403）且不改变对局状态。

---

### User Story 3 - 对局进行到后期仍能快速挑出值得看的局（Priority: P2）

当同时进行的对局超过 6 局，大厅自动切换为紧凑列表，并支持筛选（全部 / 真人局 / 决赛圈）、排序（观战人数 / 最新开局）、上滑加载更多。

**Why this priority**：参赛演示期间会长尾运行，局数会自然增长到几十上百。没有筛选与分页，大厅会变成一个不可用的大表格。它是 US1 的规模化延伸，可以独立上线。

**Independent Test**：构造 30 局进行中的对局，验证首屏只渲染 10 条、筛选「真人局」后只剩真人房、上滑能加载到第 30 条且无重复。

**Acceptance Scenarios**：

1. **Given** 大厅存在 30 局，**When** 玩家打开列表，**Then** 首屏返回并渲染 10 条，底部提示「还有 20 局」。
2. **Given** 列表已加载 10 条，**When** 玩家上滑到底，**Then** 追加下 10 条，且与已加载项无重复、无缺失。
3. **Given** 玩家选择筛选「真人局」，**When** 列表刷新，**Then** 只展示含真人玩家的对局；无匹配时展示筛选空态而非全局空态。

---

### User Story 4 - 观战中的局势可读（Priority: P2）

观战页用阵营存活进度、身份座位卡、每晚时间轴表达"现在谁占优、昨晚发生了什么"；白天投票阶段以逐票动画 + 实时得票条呈现。

**Why this priority**：观战的留存取决于"3 秒内看懂局势"。纯事件流文字对路人门槛过高。它依赖 US1/US2 的数据契约，故排在其后。

**Independent Test**：进入一局第 3 天的观战，能读到双方存活人数、已出局玩家身份与死因、当前票型；投票阶段票数增长与事件流一致。

**Acceptance Scenarios**：

1. **Given** 观战第 3 天投票阶段，**When** 玩家查看票型区，**Then** 每名被投者的得票数与已发生的投票事件严格一致（不做乐观估算）。
2. **Given** 一局结束，**When** 观战者查看结算，**Then** 能看到每晚时间轴（谁死了、死因、是否被救）与最终阵营胜负。

---

### Edge Cases

- **对局在观战中途结束**：观战视图切换到结算态并保留完整事件流，不出现"空白页"或 404。
- **对局被异常中止（LLM 失败）**：观战者看到明确的中止原因与「重开一局」入口，不展示伪造的结局。
- **同一浏览器同时开两个标签页观战同一局**：两页都正常推进，互不影响；不产生重复 `action`。
- **观战链接指向已过期的房间（>2 小时被清理）**：展示「对局已结束/已过期」，并提供回大厅入口。
- **服务端重启导致房间丢失**：观战页在 3 次轮询失败后提示「对局已失效」，不无限转圈。
- **大厅并发拉取**：两个客户端同时上滑分页，不得出现重复条目或跳过条目。

## Requirements *(mandatory)*

### Functional Requirements

**大厅列表**

- **FR-001**: 当客户端请求大厅列表时，系统 MUST 返回全部进行中对局的摘要，字段包含：对局 ID、房主显示名、当前人数、人数上限、阶段标签、天数、存活数与总数、观战人数、创建时间。
- **FR-002**: 系统 MUST 支持 `limit` / `offset`（或等价游标）分页，默认每页 10 条，单页上限 50 条。
- **FR-003**: 系统 MUST 支持按以下维度筛选：全部、含真人玩家、决赛圈（存活 ≤ 3 或进入最终投票）。
- **FR-004**: 系统 MUST 支持排序：按观战人数降序（默认）、按创建时间降序。
- **FR-005**: 如果大厅无对局，系统 MUST 返回空数组而非错误，前端 MUST 展示引导性空态。
- **FR-006**: 系统 MUST 在列表项中标注对局是否可被观战；不可观战的局（已结束、中止、正在清理）MUST 被排除在列表之外。

**观战**

- **FR-007**: 当观战者请求进入某局观战时，系统 MUST 建立只读会话并返回该局的脱敏快照与完整历史事件流。
- **FR-008**: 观战快照 MUST 包含全部玩家身份与阵营；MUST NOT 包含「某玩家正在执行某夜间行动」的实时明文。
- **FR-009**: 如果观战者提交任何会改变对局的 `action`，系统 MUST 以 403 拒绝，且对局状态不变。
- **FR-010**: 当对局产生新事件时，观战者 MUST 在 2 秒内（轮询周期 1.2s）收到增量事件，且事件顺序与对局内一致。
- **FR-011**: 如果对局在观战期间结束或中止，系统 MUST 向观战者推送终局事件，前端 MUST 切换到结算/中止态。
- **FR-012**: 如果房间已过期被清理，系统 MUST 返回明确的失效状态码与提示，前端 MUST 引导回大厅。

**投票与局势可视化**

- **FR-013**: 当对局进入投票阶段，系统 MUST 在对局页与观战页展示实时票型，得票数只能来自已发生的投票事件。
- **FR-014**: 系统 MUST 向观战者提供阵营存活统计（狼 / 好人各自的存活数与初始数）。
- **FR-015**: 当一局结束时，系统 MUST 提供每晚时间轴数据（死亡玩家、死因、是否被女巫救、是否被守卫守护），供结算页渲染。

**性能与可观测**

- **FR-016**: 系统 MUST 保证大厅列表在 100 局进行中的规模下，单次请求响应 P95 < 300ms（不依赖 LLM 调用）。
- **FR-017**: 系统 MUST NOT 因观战者数量增加而增加对局内 LLM 调用次数（观战只读事件，不触发决策）。

### Key Entities

- **LobbyEntry（大厅条目）**：一局进行中对局的对外摘要。属性：对局 ID、房主显示名、人数/上限、阶段（night/day/vote + 天数）、存活/总数、观战人数、创建时间、是否含真人、是否决赛圈。
- **SpectateSession（观战会话）**：观战者与某一局的只读关联。属性：对局 ID、客户端标识、已消费的事件 `seq`、加入时间。无写入权限。
- **MatchSnapshot（对局快照，只读投影）**：按观察者身份裁剪后的对局视图。属性：阶段、天数、玩家列表（身份可见性随观察者变化）、存活状态、票型、阵营统计。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 从首页进入某局观战，操作路径 ≤ 2 次点击，且首屏内容在 3 秒内可见。
- **SC-002**: 观战者的身份泄露事件为 0：任何接口响应、事件流、日志中都不出现「非本人身份」的明文字段（以自动化断言 + 人工抽查双重验证）。
- **SC-003**: 100 局进行中时，大厅首屏（10 条）加载 P95 < 300ms，上滑加载无重复无缺失。
- **SC-004**: 观战事件的端到端延迟 P95 < 2s（从对局产生到观战者可见）。
- **SC-005**: 观战不增加对局成本：同一局在 0 个观战者与 10 个观战者下，LLM 调用次数完全相同。
- **SC-006**: 观战页在 390px 视口下无需横向滚动即可读完"阶段 + 阵营存活 + 票型"三块核心信息。

## Assumptions

- 沿用现有服务端权威架构与轮询事件流（`seq` + `?since=`），不引入 WebSocket（真人房 v2.0 再评估）。
- 房间仍在内存中保留 2 小时、上限按现有 `MAX_ROOMS` 控制；大厅规模以 100 局为目标压测上限。
- 观战不需要登录即可使用（登录只影响「我的对局」归属，属 v1.5）。
- 大厅数据来自内存房间的投影，不落库；历史对局通过现有 `ww_matches` 战绩表提供，不回放完整事件流。
- 前端若在 v1.4 期间仍为原生 JS，则本特性必须做到渲染逻辑与状态解耦，便于后续迁移到 React 而不重写契约。

## Open Questions
