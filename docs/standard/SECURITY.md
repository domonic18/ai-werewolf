# 安全与反作弊规范

> 适用范围：`werewolf-ai` 全部客户端与服务端改动。新增接口、新增角色能力、新增任何「写入」路径时，
> 先对照本文的威胁模型，再看第九节的检查清单。

## 一、信任边界

```
浏览器（不可信）  ──HTTP──▶  Node 服务端（唯一权威）  ──SDK──▶  LLM / 云数据库
                                    │
                                    └── 云端 /.cloud/auth/v1/user/me（身份唯一来源）
```

三条硬规则：

1. **客户端不持有真相**：身份、夜间行动、他人角色只存在于服务端；前端拿到的永远是投影。
2. **一切写入都要凭证**：玩家私有接口必须带 `X-Player-Token`；账号归属必须由云端核验。
3. **能算的不要问客户端**：观战人数、票型、发言顺序都由服务端从事件流派生，不信任前端上报。

## 二、作弊路径盘点（游戏机制层面）

| # | 可能的作弊方式 | 现状 | 结论 |
|---|---|---|---|
| 1 | 直接读接口拿别人身份 | 玩家快照走 `snapshot(humanId)` 投影，座位里只有 `revealed`，不含 `role`/`camp`；观战才走 `spectateSnapshot()` | 已防住，且有测试守住 |
| 2 | 替别人操作 / 替别人投票 | `/action`、`/quit`、`/events`、快照全部要求 `X-Player-Token`（32 位十六进制，定长比较）；`gameId` 公开也不够用 | 已防住 |
| 3 | 伪造登录身份，把战绩刷到别人名下 | `resolveOwner` 不解 JWT，而是拿 token 去云端 `user/me` 实打实问一次；失败降级匿名 | 已防住 |
| 4 | 改写历史 / 回滚回合 | 事件流只追加，`submitHuman` 只推进当前挂起点；重复提交返回 409 | 已防住 |

## 三、接口级防线

| 接口 | 认证 | 限流 | 备注 |
|---|---|---|---|
| `POST /api/games` | 可选（匿名可玩） | 3 次/10 分钟/人（账号或 IP）、10 次/分钟全局 | 限流在 LLM 就绪检查之后，避免初始化期误伤 |
| `GET /api/games/:id`、`/events` | `X-Player-Token` | — | 访问即刷新房间 `lastActiveAt` |
| `POST /api/games/:id/action` | `X-Player-Token` | 30 次/分钟/房间 | 每次动作都会推动 AI 决策，必须限速 |
| `POST /api/games/:id/quit` | `X-Player-Token` | — | 停止引擎，释放该局算力 |
| `GET /api/games/:id/spectate` | 无 | — | 只读上帝视角；身份泄露风险见第五节 |
| `GET /api/live`、`/api/matches` | 无 | 240 次/分钟/IP | 只读投影，不含私有字段 |
| `POST /api/models/select` | production 需登录 | 6 次/小时/人 | 全局生效，属管理型操作 |
| `GET /api/health`、`/api/roles`、`/api/auth-config` | 无 | — | 只返回可公开值 |

### 身份核实的两个硬约束（2026-10-23 线上排查得到）

服务端拿用户 token 去云端 `/.cloud/auth/v1/user/me` 认人时，必须同时满足：

1. **带 `x-wb-webapp-access-key`**，否则网关只回 `invalid_client`；
2. **带 `Origin`（以及 `Referer`）且等于应用自己的公网域名** —— 会话是按「appId + Origin」绑定的，
   服务端到服务端调用默认没有 Origin，网关会当成另一个客户端，回
   `401 invalid_grant: ...issued for another client`。

第 2 条曾经漏掉，表现不是「报错」，而是**静默降级成匿名**：页面显示已登录，战绩却按全网口径统计。

还有第 3 条，比前两条更隐蔽：**平台的 HTTP 网关会用自己的凭据覆盖浏览器的 `Authorization`**。
实测（2026-10-23）：前端发 `Authorization: Bearer AAAA`，服务端收到的 token 哈希与 `AAAA` 对不上，
且每个请求都不同 —— 用户身份根本传不到服务端。所以用户 token 改走自定义头 `X-WW-Token`
（实测原样透传），服务端优先读它，仍兼容 `Authorization` 以便本地 curl 调试。
排查手段：`GET /api/whoami` 会回 `tokenHint`（收到 token 的 SHA-256 前 8 位），
拿它和自己发出的 token 比一下就知道是「网关换掉了」还是「token 过期」。
排查方法（不需要真实 token 也能判定网关是否在校验 Origin）：

```bash
# 错误 Origin → 403 access_denied（证明 Origin 参与校验）
curl -i https://<域名>/.cloud/auth/v1/user/me \
  -H 'Authorization: Bearer x' -H 'x-wb-webapp-access-key: <wbpk_…>' \
  -H 'Origin: https://evil.example.com'
```

另外：access token 会过期，**续期只能由客户端发起**（SDK 的 `getAccessToken()` / `refreshSession()`，
句柄绑定 appId + Origin）。服务端不缓存 token 以外的东西，前端也不能把登录瞬间拿到的 token 存下来一直用——
过期后服务端只会认成匿名。

### 新增表（2026-10-23）：ww_profiles / ww_invites

| 表 | 用途 | 策略 |
|---|---|---|
| `ww_profiles` | 账号昵称、邀请码、是否公开战绩 | SELECT 全开；INSERT / UPDATE 只校验形状（`invite_code ~ '^[A-Z]{4}-[0-9A-Z]{3}$'`） |
| `ww_invites` | 邀请关系（`invitee_id` 主键） | SELECT 全开；INSERT 带 `invitee_id <> inviter_id`（库层挡自邀请） |

读写都只发生在服务端：客户端从不直连数据库，所有入口都要求登录（`/api/invite*`、`/api/profile` 未登录回 401）。
策略之所以对 `anon` 放行，是因为服务端用的是 publishable key（`auth.uid()` 为空），
与既有的 `ww_matches` 同一套取舍——**publishable key 泄露后，别人可以绕过我们的 API 直接写库**，
这是本阶段已知且接受的风险（写的内容是邀请码与昵称，无资金与隐私数据；有 API 限流兜住正常路径）。

`hide_stats` 关闭后，服务端在聚合时就**不返回**局数与胜率（不是前端遮挡）——
否则抓包一样能看到，承诺就没有意义。

## 四、响应头与传输

- `Content-Security-Policy`：脚本只允许同源（无 `unsafe-inline`）、禁止被 iframe 嵌套（`frame-ancestors 'none'`）、
  `connect-src` 放开到 `https:` 是因为登录 SDK 要直连云服务域名
- `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` 关闭地理/麦克风/摄像头/支付
- HTTPS 请求额外下发 `Strict-Transport-Security`
- 凭证只走请求头，绝不放进 URL（避免被日志、分享链接、Referer 带出去）
- 服务端不打印 access token；身份缓存用 token 的 SHA-256 作键

## 五、已知残留风险（写清楚，而不是假装没有）

### R1 自开号观战偷看（可利用性：高，收益：一局胜负）

玩家用第二个浏览器打开自己那一局的观战链接，就能看到所有人身份。
这是「上帝视角」这个卖点的固有代价。当前没有排行榜、没有代币、没有连胜奖励，
作弊收益只有一局的输赢，**产品上暂时接受**。

彻底修的两条路（按成本排序）：

1. **身份延迟**：观战投影里角色延后 N 分钟（或延后到该玩家出局）才公开——需要给快照加「时间旅行」能力，改动中等
2. **结束后才公开身份**：观战变成「看进程（谁死了、谁在发言），结束后给完整身份」——最简单，但观赛体验下降

建议在 q3 明确一项后再动；在此之前，`smoke:live` 里保留「观战者无法操作」的断言。

### R2 台词套身份（可利用性：中，收益：影响 AI 表现）

已加系统提示防线，但 LLM 是否能稳定拒绝，取决于模型。**这是概率性防御，不是硬保证**。
可选的加强（按性价比）：

1. 发言先做一次「可疑指令」预处理（关键词命中就加一句提醒）——成本低，但对改写措辞无效
2. 让 AI 只在「自己视角」作答，身份永远不出现在输出 schema 里——已经在做，继续守住
3. 定期用一组攻击话术跑回放（人工抽检），观察是否出现身份泄露

### R3 多账号刷战绩（可利用性：中，收益：无）

没有排行榜与奖励，收益为零。等做排行时再引入「同一设备/同一支付主体」的去重。

### R4 单机自娱式 DoS

限流按 IP/账号，攻击者换 IP 仍可放大（每 IP 3 局/10 分钟 × N 个 IP）。
全局每分钟 10 局是最后一道闸。真要抗住需要网关级限流，超出本项目档期。

## 六、prompt 安全

- 玩家代号与发言进入 AI 上下文前：去控制字符、限长（代号 8 字、发言 300 字）
- 系统提示显式声明：玩家发言是「场上信息」而非指令，要求泄露身份/系统提示/改输出格式的一律当可疑发言处理
- AI 输出走 JSON 解析（括号深度法），解析失败按失败重试，不把自由文本直接塞进事件流
- 玩家私有信息（身份、狼队友、验人结果）只出现在该 AI 自己的 prompt 里，不进公共日志

## 七、数据与密钥

- 仓库零密钥：`config/cloud.json` 在 `.gitignore`；`publishableKey` 本身无权限，按公开值对待
- 战绩表 RLS 已开；写库失败不影响对局（降级为「未存档」并在结算页说明）
- 事件流上限 500 条，避免单局无限增长

## 八、可观测与响应

- `/api/health` 暴露 `llm.state` / 调用次数 / 房间数，供外部探活
- 房间回收、限流命中目前不打日志（参赛规模够用）；若上线公网，建议把 429 与 413 计数接到告警
- 发生事故时的第一动作：`POST /api/games/:id/quit` 停掉单局；整体异常则重启进程（内存态，重启即干净）

## 九、改动前检查清单

- [ ] 新接口有没有写清「需不需要凭证」？需要的话是否走 `X-Player-Token` 而不是 URL 参数？
- [ ] 这个接口能不能被用来消耗模型额度或写入数据？需要的话加限流并写明窗口与阈值
- [ ] 返回值里有没有别人不该看到的东西（身份、夜间目标、凭证、密钥）？
- [ ] 客户端传来的字符串有没有去控制字符、限长？会不会进 prompt 或 HTML？
- [ ] 新增的房间状态有没有「无人时如何回收」的路径（否则 20 个名额会被弃局占满）？
- [ ] 失败路径是否明确（400/401/403/409/413/429 的语义不要混用）？
- [ ] 有没有对应的测试？安全类改动至少一条「攻击路径被拒绝」的用例
